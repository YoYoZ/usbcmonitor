# Запасные пути

Пробовать в этом порядке — от дешёвого к дорогому. Для каждого пути ниже
оставлена таблица "что сработало / что нет / почему" — заполнять по факту
испытания на реальной плате, не оставлять как есть.

## План А.1 — явный формат между v4l2jpegdec и kmssink

Если базовый пайплайн падает на `not negotiated` между декодером и sink:

```bash
gst-launch-1.0 -v v4l2src device=/dev/v4l/by-id/<камера> io-mode=dmabuf \
  ! image/jpeg,width=1920,height=1080,framerate=25/1 \
  ! v4l2jpegdec \
  ! video/x-raw,format=NV12 \
  ! v4l2convert \
  ! video/x-raw,format=NV12 \
  ! kmssink sync=false
```

`v4l2convert` — это тоже аппаратный путь (через ISP VideoCore, отдельный
M2M-узел `bcm2835-codec-isp`), а не программная перекраска — на Zero
программный `videoconvert` для 1080p25 отдельно от декода уже может не
уложиться в бюджет одного ядра.

## План А.2 — io-mode=mmap вместо dmabuf (или наоборот)

Если один из режимов даёт `VIDIOC_REQBUFS failed` или зависание без кадров —
поменять `io-mode` местами на `v4l2src` и убедиться, что `v4l2jpegdec` не
форсирует несовместимый режим (можно оставить `v4l2jpegdec` без явного
`io-mode`, чтобы он сам договорился).

## План Б — mpv с v4l2m2m-copy через DRM

Не требует ручной сборки GStreamer-пайплайна, использует тот же
`bcm2835-codec` под капотом через ffmpeg-декодер `mjpeg_v4l2m2m`:

```bash
sudo apt install -y mpv   # ffmpeg входит как зависимость с поддержкой v4l2m2m в Raspberry Pi OS
mpv --no-config --vo=drm --drm-connector=HDMI-A-1 \
    --hwdec=v4l2m2m-copy --hwdec-codec=mjpeg \
    --untimed --no-cache --profile=low-latency \
    /dev/v4l/by-id/<камера>
```

Важно: это использует **тот же самый** `/dev/video10`, что и `v4l2jpegdec` —
если план А.1/А.2 упёрлись именно в отсутствие MJPG в
`--list-formats-out` декодера (шаг 4 отладки), этот путь **тоже не заработает**,
он не является независимой альтернативой в этом случае. Он полезен, если
проблема была именно в GStreamer-обвязке (буферизация, негоциация), а не в
самом драйвере.

## План В — ffmpeg напрямую с mjpeg_v4l2m2m

```bash
ffmpeg -f v4l2 -input_format mjpeg -video_size 1920x1080 -framerate 25 \
  -i /dev/v4l/by-id/<камера> \
  -c:v mjpeg_v4l2m2m \
  -f fbdev /dev/fb0   # если нет /dev/fb0 (чистый KMS) — см. вариант с kmssink ниже через ffmpeg's `kmsgrab`/`drm` вывод не тривиален
```

На практике вывод из ffmpeg напрямую в KMS не так прост, как через
GStreamer `kmssink` (нет готового простого sink), поэтому этот план — скорее
диагностический (проверить, декодирует ли ffmpeg вообще, сравнить с планом Б),
чем финальное решение. Тот же нижележащий драйвер, что и в плане А — не
независимая проверка при отсутствии MJPG на входе декодера.

**Результат:** _(заполнить)_

## План Г (последний вариант) — legacy OMX, `omxmjpegdec`

Только на Bullseye (Bookworm не поддерживает легаси GL/MMAL стек официально).
**Текущая карта — Bookworm**, для этого плана придётся перепрошить образ
Bullseye из архива (см. [01-hardware-and-risks.md](01-hardware-and-risks.md)).

```bash
sudo apt install -y gstreamer1.0-omx libraspberrypi-bin libraspberrypi0
gst-inspect-1.0 | grep -i omx   # проверить, что omxmjpegdec вообще зарегистрирован
```

Если `omxmjpegdec` присутствует:

```bash
gst-launch-1.0 -v v4l2src device=/dev/v4l/by-id/<камера> \
  ! image/jpeg,width=1920,height=1080,framerate=25/1 \
  ! omxmjpegdec \
  ! kmssink sync=false
```

Это исторический путь, который в современных Raspberry Pi OS уже не
является приоритетным (Raspberry Pi Foundation официально продвигает V4L2
M2M вместо OMX с версии Bullseye), поддержка `omxmjpegdec` конкретно под
вопросом — не факт, что элемент вообще зарегистрируется в актуальном
`gstreamer1.0-omx` из репозитория Bullseye. Документировать как крайний
случай, как и указано в задаче, не тратить на него время, пока не испробованы
планы А и Б.

## Если ничего из аппаратных путей не завелось

Честный ответ по ограничениям задачи: программный декод 1080p25 MJPEG на
одном ядре ARMv6 в реальном времени физически недостижим. Минимальная
адекватная альтернатива в этом случае — не "городить" через
многопоточный software JPEG decoder, а:

1. Понизить требования: если камера поддерживает более низкое разрешение
   /fps по UVC (перепроверить шаг 3 — возможно, там больше одного режима,
   вопреки исходному предположению) — использовать его вместо 1080p25.
2. Либо признать, что задача "1080p25 в реальном времени на Zero v1 без
   рабочего аппаратного MJPEG-декода" не решается на этом железе, и
   предложить пользователю Pi Zero 2 W (тот же форм-фактор, но 4-ядерный
   Cortex-A53) как минимальный шаг вверх по железу — это уже не про софт,
   а про то, что задача прямо просит сказать честно, если что-то
   невозможно на Zero v1.
